# FlyWire Framework Architecture Review

## Section 1 — Repository Architecture
**How is the project organized?**
The repository is structured into distinct top-level directories:
- `core/`: Contains the foundational orchestration, data loading, graph building, and result aggregation (`data_loader.py`, `graph_builder.py`, `experiment_runner.py`, `statistics_engine.py`, `export_manager.py`).
- `modules/`: Contains domain-specific implementations organized by pipeline stage (`preprocessing/`, `error_models/`, `graph_analyses/`, `downstream_tasks/`).
- `configs/`: Stores YAML configurations (though currently only containing an empty `defaults.yaml`).
- `research_data/`: Contains placeholder directories (`raw/`, `cache/`, `checkpoints/`, `experiments/`, `logs/`) for dataset storage.
- `results/`: Output directory for generated research artifacts.
- `docs/`, `notebooks/`, `tests/`: Standard supplementary directories.

**Which modules own which responsibilities?**
- `core.experiment_runner`: Acts as a pure orchestrator coordinating the pipeline. Contains no domain logic.
- `core.data_loader`: Loads raw CSVs into memory using `pandas`.
- `core.graph_builder`: Converts `pandas` DataFrames into `networkx.DiGraph` objects.
- `modules.preprocessing`: Orchestrates graph validation, metadata generation, and lookup indexing (`pipeline.py`).
- `modules.error_models`: Defines the perturbation contract (`BaseErrorModel`) and registries.
- `modules.graph_analyses`: Defines the contract for feature extraction/analysis.
- `core.export_manager`: Packages completed experiments into structured artifacts.

**Is the architecture modular or tightly coupled?**
The architecture is highly modular and follows a strict registry-based, configuration-driven pattern. The `ExperimentRunner` depends on abstractions (`PreparedGraph`, `ErrorRegistry`, `AnalysisRegistry`) rather than concrete implementations, enforcing strong separation of concerns.

## Section 2 — Data Loading
**Which library is used?**
The framework exclusively uses `pandas` (`pd.read_csv`).

**Are FlyWire IDs preserved?**
Yes. Columns such as `root_id`, `pre_root_id`, and `post_root_id` are explicitly preserved and utilized as node and edge identifiers.

**Are IDs downcast?**
Not implemented. There is no explicit downcasting logic; pandas infers the types, which likely default to `int64`.

**Are IDs remapped?**
IDs themselves are not mutated. However, dataset-specific column names are normalized via `PRINCETON_MAPPING` and `FAFB_MAPPING` in `core/data_loader.py`.

**Is any information discarded?**
No. `GraphBuilder._add_nodes` and `GraphBuilder._add_edges` explicitly iterate over all remaining dataframe columns and attach them as node or edge attributes.

**Current implementation**
- **Strengths:** Highly standardized schema normalization (`FlyWireDataset`). Simple, easy-to-understand data mapping.
- **Weaknesses:** Pandas is notoriously inefficient for memory and CPU when loading multi-gigabyte connectomes. Gzip decompression via Pandas is single-threaded and slow.
- **Required future changes:** Replace `pandas` with `polars` or `pyarrow` to implement lazy loading, zero-copy memory operations, and explicit downcasting of 64-bit IDs.

## Section 3 — Graph Construction
**Graph library**
The framework uses `NetworkX` (`nx.DiGraph`).

**How graph is constructed**
`core/graph_builder.py` iterates over the rows of the normalized pandas DataFrames (`itertuples`) and populates the graph via `add_nodes_from` and `add_edges_from`.

**Are IDs mapped / Are IDs copied?**
NetworkX stores nodes in a native Python dict-of-dicts structure. The IDs are passed as dictionary keys, resulting in copies of the IDs and their associated attribute dictionaries residing in the NetworkX internal memory structure.

**Are graphs rebuilt repeatedly?**
In the current runner logic, the baseline graph is built once per `ExperimentConfig` execution. However, perturbations involve deep copies (see Section 8).

**Memory behavior**
Extremely inefficient. The dict-of-dicts structure in NetworkX carries enormous memory overhead for large-scale graphs (millions of edges), effectively duplicating the RAM footprint of the original Pandas DataFrames.

**Potential bottlenecks / Compatibility with Kaggle**
This design is strictly incompatible with Kaggle's 30GB RAM limit. Building a NetworkX `DiGraph` for the full FlyWire connectome will cause an Out-Of-Memory (OOM) crash before graph construction even finishes.

## Section 4 — Graph Storage
**How graphs are stored**
Graphs are stored in memory as `nx.DiGraph` instances, wrapped inside a `PreparedGraph` contract object (from `modules/preprocessing/prepared_graph.py`).

**One graph or multiple graphs or graph copies?**
Multiple copies. 
The pipeline creates the initial `nx.DiGraph`. When an error model is applied, `modules/error_models/base_error_model.py` executes `graph_copy = prepared.graph.copy()`, creating an explicit secondary deep copy of the entire network.

**Which objects remain in memory?**
Throughout a single experiment, the following objects simultaneously reside in memory:
1. The raw `pandas` DataFrames.
2. The baseline `nx.DiGraph` (inside `PreparedGraph`).
3. The perturbed `nx.DiGraph` (inside `ErrorResult`).

**Current memory lifecycle**
Data is loaded, duplicated into a graph, duplicated again into a perturbed graph, and all copies survive until the `ExperimentResult` is destroyed or garbage collected. This lifecycle represents exponential memory bloat.

## Section 5 — Feature Extraction
**Which node features already exist?**
Not implemented. While `centrality.py` and `community_detection.py` exist in `modules/graph_analyses/`, the files are completely empty.

**Which edge features already exist?**
Not implemented.

**Are features computed once or computed every experiment?**
According to the `ExperimentRunner` workflow, analyses are executed dynamically as part of `run_analyses()`. Since the target graph is perturbed dynamically per experiment, features would be re-computed from scratch during every experiment trial.

**Current workflow**
The runner instantiates analyses via the registry and executes them on the `PreparedGraph` (baseline or perturbed).

## Section 8 — Perturbation Engine
**Exactly how perturbation is currently performed**
`modules/error_models/base_error_model.py` executes:
`graph_copy = prepared.graph.copy()`
The concrete subclass is then expected to modify `graph_copy` in-place. The docstring implies edges are removed via `graph_copy.remove_edges_from()`, but actual concrete perturbation logic is Not implemented.

**How randomness is handled**
`BaseErrorModel._init_seed(seed)` calls `import random; random.seed(seed)`.

**What objects are modified**
Only the newly created deep copy of the `nx.DiGraph` is modified. The original baseline graph is strictly immutable.

**Whether perturbation depends on graph topology**
Not currently implemented.

## Section 10 — Experiment Runner
**Overall workflow**
Load Dataset → Build Graph → Preprocess Graph → (Optional) Apply Error Model → Run Analyses → Aggregate Results.

**How are datasets iterated?**
The runner is stateless. Iteration must be handled by an external loop that generates and submits multiple `ExperimentConfig` objects to `runner.run()`.

**How are seeds handled?**
Passed via `ExperimentConfig.seed` and explicitly routed to `ErrorModel.execute()`, which initializes the global Python `random` seed.

**How are error levels handled?**
Configured via `ExperimentConfig.error_model_config` dict (e.g., `{"removal_rate": 0.05}`).

**Is there caching?**
Not implemented. 

## Section 11 — Runtime Behaviour
**Memory lifecycle**
Load (Pandas DFs) → Build Graph (NetworkX Graph) → Preprocess → Perturb (NetworkX Deep Copy) → Analyses → Export.

**Which objects survive**
The `ExperimentResult` object retains references to both the baseline `PreparedGraph` and the `ErrorResult` (containing the perturbed graph). The memory footprint continually expands until the runner finishes and the result object falls out of scope.

**Which objects are destroyed**
None explicitly during the execution of one pipeline run.

## Section 12 — Memory Analysis
**Largest objects**
1. Baseline `nx.DiGraph`
2. Perturbed `nx.DiGraph` copy
3. Original `pandas` DataFrames

**Memory duplication**
The framework maintains at least three full in-memory representations of the biological dataset simultaneously, plus high-overhead dictionary allocations from NetworkX. Repeated graph construction and repeated loading across multiple runs compound this issue.

**Major RAM bottlenecks**
- NetworkX graph construction.
- NetworkX deep copy (`graph.copy()`) inside the error model framework.
- Pandas CSV parsing.

## Section 13 — Performance Analysis
**Computational bottlenecks**
1. **NetworkX deep copy**: Copying dict-of-dicts for large graphs is incredibly CPU and RAM intensive.
2. **Repeated loading**: `pandas.read_csv` on large compressed files for every experiment.
3. **Repeated graph construction**: Rebuilding the NetworkX topology structure.

**Top performance issues**
1. Use of NetworkX for massive connectomes.
2. Explicit object copying instead of view-based or edge-weight perturbations.

## Section 14 — Output Pipeline
**What outputs currently exist**
`core/export_manager.py` produces:
- `metadata.json`
- `config_snapshot.yaml`
- `summary.csv`
- `trial_results.csv`
- `runtime_report.txt`
- `README.md`
- Optional `.zip` bundle

**Where outputs are generated**
Stored in timestamped sub-directories based on the `experiment_id` within the provided output root (e.g., `results/`).

**What metadata is stored**
Full configuration snapshots, random seeds, framework versions, runtimes, status states, detailed perturbation metadata, and flattened analysis metrics.

## Section 15 — Reproducibility
**Whether framework records...**
- Random seed: Yes
- Configuration: Yes
- Dataset: Yes
- Runtime: Yes
- Version: Yes (`_FRAMEWORK_VERSION = "1.0.0"`)
- Parameters: Yes

**How reproducible experiments currently are**
Highly reproducible in terms of configuration parameters and seed logging. However, the lack of dataset versioning and the reliance on standard Python `random` (instead of numpy random states) could introduce slight stochastic drifts across different execution environments.

## Section 16 — Kaggle Compatibility Assessment
**Evaluate Current implementation against Kaggle constraints**
The current implementation **cannot safely run** the largest FlyWire graph on Kaggle. 
- **RAM usage:** Kaggle limits RAM to ~30GB. NetworkX dict-of-dicts and `pandas` DataFrames, coupled with the explicit `graph.copy()` mechanism, will instantly trigger OOM kills on massive connectomes.
- **Repeated graph construction:** Intolerable overhead within a Kaggle notebook timeframe (12 hours).
- **Large object duplication:** Unacceptable for limited memory environments.

## Section 17 — Gap Analysis

| Component | Current State | Missing Functionality | Required Changes | Priority |
| :--- | :--- | :--- | :--- | :--- |
| **Data loading** | `pandas.read_csv` | Type downcasting, lazy evaluation | Move to Polars/PyArrow. | High |
| **Graph construction** | `networkx` | Memory efficiency, array-based storage | Switch to contiguous array (NumPy edge lists) or `graph-tool`/`igraph`. | Critical |
| **Graph storage** | Multiple `nx.DiGraph` copies | Immutable single reference | Store single baseline, track perturbations as arrays. | Critical |
| **Feature extraction** | Empty files | Algorithms not implemented | Implement algorithms using matrix operations. | High |
| **Vulnerability computation** | Not implemented | Biological scoring | Implement feature-based scoring model. | High |
| **Probability calibration** | Not implemented | Score-to-probability mapping | Implement calibration curves. | High |
| **Perturbation** | `nx.DiGraph.copy()` | In-place weight mutation | Refactor to mutate edge weights rather than structure. | Critical |
| **Validation** | Implemented (nx based) | Array-based validation | Refactor to validate array indices. | Medium |
| **Experiment runner** | Implemented | Loop-level batch execution | Update to run over mutated arrays, not graph copies. | High |
| **Runtime monitoring** | Minimal logging | Memory/CPU profiling | Add telemetry to catch Kaggle limits. | Low |
| **Output generation** | Implemented | - | - | Low |

## Section 18 — Refactoring Roadmap

1. **`core.data_loader`**: **Modify**. Transition from Pandas to Polars to enforce schema downcasting (e.g., `uint32` for IDs) and lazy loading to drastically reduce initial RAM spikes.
2. **`core.graph_builder`**: **Replace**. Remove NetworkX entirely. Construct a highly optimized, array-backed graph representation (e.g., CSR matrix, standard NumPy edge arrays, or `graph-tool` base).
3. **`modules.error_models.base_error_model`**: **Modify**. Remove `graph_copy = prepared.graph.copy()`. Enforce a paradigm where perturbations modify a lightweight detached edge-weight mask or array instead of the topology.
4. **`modules.error_models.missed_synapses`**: **Keep / Implement**. Implement the missing biological vulnerability model and probability calibration directly against the new array-based graph structures.
5. **`modules.graph_analyses`**: **Keep / Implement**. Implement centrality and community algorithms utilizing array-optimized logic (e.g., SciPy sparse matrices).
6. **`core.experiment_runner`**: **Modify**. Adjust the contract to pass the single immutable graph and the perturbation masks to downstream analyses instead of passing deeply copied topological graphs.
7. **`modules.preprocessing`**: **Modify**. Refactor `validator` and `pipeline` to validate the new array/Polars structures instead of `nx.DiGraph` methods.
8. **`core.statistics_engine` & `core.export_manager`**: **Keep**. Architecture here is sound and decoupled from the graph memory footprint. No changes needed.
